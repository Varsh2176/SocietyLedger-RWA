# SocietyLedger deployment

This is the preparation procedure. It does not deploy the application or copy any database.

## Architecture

- Frontend: Vite static site on Render (`societyledger-web`), with an SPA rewrite to `index.html`.
- Backend: Node web service on Render (`societyledger-api`), start command `npm start`, listening on `0.0.0.0:$PORT`.
- Database: the existing MongoDB Atlas cluster. Render does not host this database.
- Documents: private files under `UPLOADS_DIR`. The Blueprint attaches a 1 GB disk at `/var/data` and sets `UPLOADS_DIR=/var/data/uploads`. That disk requires a paid web service, stays on one instance, and is not shared. Do not treat persistence as verified until an upload and download succeed after a restart.

The API and the site are different hosts, so the production session cookie is `Secure` and `SameSite=None`. Local development stays `SameSite=Lax`.

## Atlas database

1. In the Atlas project, open `ClusterSL`.
2. Database Access: create a database user that can read and write only the `society_ledger` database. Do not use the Atlas organization owner as the application user.
3. Network Access: allow only the Render outbound addresses you actually use. Avoid `0.0.0.0/0` when a narrower list is available. Render web services do not have one fixed IP on every plan, so a temporary allow-all is a known limitation if the plan cannot use a static egress IP.
4. Connect: copy the SRV URI and set the path to `/society_ledger`. Store it only as the `MONGODB_URI` environment variable on the API service.
5. Do not run `npm run seed`. That script deletes and recreates Greenwood Heights demo records.

## Moving local data later

Do this only after an explicit decision to copy data, and never as part of the first deploy.

1. Stop writes to the source database.
2. Take an Atlas or `mongodump` backup of the destination before import.
3. Dump only the intended database from the local `society_ledger` database.
4. Restore into the empty Atlas `society_ledger` database.
5. Compare collection counts, including funds, transactions, documents, reconciliations, and audit logs.
6. Confirm Greenwood Heights still has its original fund and transaction counts before announcing the site.

Do not import the disposable verification society or its files.

## Environment variables

API service:

| Name | Purpose |
| --- | --- |
| `NODE_ENV` | `production` |
| `PORT` | Set by Render. Do not hardcode it. |
| `MONGODB_URI` | Atlas SRV URI, database path `society_ledger` |
| `JWT_SECRET` | Random secret generated by Render |
| `COOKIE_SECRET` | Random secret generated by Render |
| `JWT_EXPIRES_IN` | `1d` |
| `CLIENT_URL` | Exact frontend origin, no path, comma-separated if more than one |
| `UPLOADS_DIR` | `/var/data/uploads` when the disk is attached |

Web service:

| Name | Purpose |
| --- | --- |
| `VITE_API_BASE_URL` | API origin, for example `https://societyledger-api.onrender.com`. The app appends `/api` when needed. This is public and is not a secret. |
| `VITE_ENABLE_MOCK_FALLBACK` | `false` |

Set `VITE_API_BASE_URL` before the frontend build. A production build fails if that value is missing or points at localhost. Changing it later requires a new frontend build.

## Deploy order, after approval

1. Sync the Blueprint or create the two services manually. Leave auto-deploy off until the variables above are set.
2. Deploy the API. `GET /api/health` must return HTTP 200 and `database.status` of `connected`.
3. Set `CLIENT_URL` to the frontend origin and redeploy the API if the first health check happened before that value existed.
4. Set `VITE_API_BASE_URL` to the API origin and deploy the frontend.
5. Add custom domains in the Render dashboard if you have them. Render provisions HTTPS. Point `CLIENT_URL` and `VITE_API_BASE_URL` at those HTTPS origins and rebuild the frontend.
6. Sign in, open the dashboard, and confirm the browser calls the deployed API rather than `localhost`.

## Rollback

- Render keeps previous deploys. Roll back the API or the static site from the service's deploy list.
- Rolling back does not restore MongoDB writes. Restore Atlas from a backup if a later migration damages data.
- The upload disk is not rolled back with the code. Snapshot or copy it before changing the disk.

## Production database initialization

Do not run this until it has been explicitly approved. Do not run `npm run seed`. The bootstrap creates only the Greenwood Heights RWA society and one Society Administrator. It does not copy local users, funds, transactions, documents, or reconciliations.

From `backend/`, the command is `npm run bootstrap:production`. It writes nothing unless every check below passes:

- `BOOTSTRAP_CONFIRM` is `INITIALIZE_GREENWOOD_HEIGHTS`.
- `MONGODB_URI` is set in the environment. The command does not read `backend/.env`.
- `BOOTSTRAP_ADMIN_NAME`, `BOOTSTRAP_ADMIN_EMAIL`, and `BOOTSTRAP_ADMIN_PASSWORD` are set. The password must be at least 12 characters and must not be a development password. The email must not be one of the demo `@society.org` accounts.
- An Atlas URI also requires `NODE_ENV=production` and `CONFIRM_ATLAS_INIT=YES`.
- The local `society_ledger` database is refused unless `ALLOW_LOCAL_LEDGER_INIT=YES`. Leave that unset.

A second run keeps the existing society, invitation code, administrator, and password. The password is hashed by the User model and is not printed. The invitation code is printed once so it can be stored for resident registration. A newly created code is random and is not the public demo code `GW-2021`.
